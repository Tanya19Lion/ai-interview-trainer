## Section B — drift findings

1. **Endpoint ↔ data-model** — ✓. `login` reads `User`, upserts `LoginAttempt` (rate-limit
   counter); `register`/`googleLogin` write `User`; `refreshSession` reads `User.tokenVersion`;
   `logout` writes `User.tokenVersion` (bump). Both entities in `data-model.md` are touched by
   ≥1 endpoint.
2. **Error codes ↔ domain sentinels** — **deferred to implementation time**, same as
   `forgot-password`'s finding. No error-constants module exists in `src/` (existing auth errors
   are inline strings in `auth.controller.ts`); this feature's endpoint changes are unimplemented
   — contract precedes code. Not scored as a failure per protocol's explicit allowance.
3. **Validation ↔ persistence constraints** — ✓. `email`/`password`/`name` inherit their existing
   constraints from `User`'s schema (unique email, `PASSWORD_MIN_LENGTH = 8`). `rememberMe` has no
   persistence-layer equivalent to check against — correctly so, since it is never persisted (see
   Section A note); not a gap.
4. **Entity ↔ endpoint** — ✓, with one note. `User` is served by all 5 endpoints. `LoginAttempt`
   is never itself exposed by any endpoint — **intentionally internal**, the same pattern
   `forgot-password`'s report used for `PasswordReset`-adjacent internal state: it exists purely
   as a server-side rate-limit counter, surfaced to the client only indirectly via the `login`
   429 response, never as its own resource.
5. **OpenAPI ↔ sequence** — ✓ (resolved 2026-09-10). `complete-sequence-diagrams` added 6
   endpoint-level `### US-N:` sequences with `alt` blocks to `sad.md` §6 (`_audit/
   sequences-2026-09-10.md`). `login`'s 3 branches (US-01) and `refreshSession`'s 2 branches
   (US-02) now trace to real `alt`-blocks, not just PRD/ADR prose: `400
   auth.missing_credentials`, `401 auth.invalid_credentials`, `429 auth.rate_limited` for
   `login`; `401 auth.refresh_token_expired`, `401 auth.session_revoked` for `refreshSession`. All
   five match `openapi.yaml`'s response codes exactly.
