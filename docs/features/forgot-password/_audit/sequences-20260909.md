## Added

- **US-01** — Request a password reset. `alt` branches: unknown email (AC-02), known account
  under rate limit (AC-01), rate limit exceeded (429, PRD §6 NFR), Google-only account (AC-05).
- **US-02** — Set a new password via reset link. `alt` branches: valid token (AC-01), invalid/
  expired/used token (AC-03). Notes the atomic `findOneAndDelete` single-use guarantee.
- **US-03** — Change password while logged in. `alt` branches: Google-only account, no
  `passwordHash` (AC-05), wrong current password (AC-04), success + `tokenVersion` bump (AC-06).
- **US-04** — Understand why reset doesn't apply to a Google account. Both PRD-named entry
  points (request-reset, change-password screen) shown as two `alt` branches converging on the
  same explanatory message — no dead end from either entry point (AC-05).
- **US-05** — Reset link expires or becomes invalid. `alt` branches: TTL-expired vs
  already-used (single-use consumed) — both collapse to the same `400
  password_reset.invalid_or_expired_token` response (AC-03).

Existing "Critical flow 1" and "Critical flow 2" left untouched (additive-only rule) — some
happy-path overlap with US-01/US-02/US-04 is expected and acceptable.

## ADR potential

- **US-01**: rate-limiting mechanism for *unregistered* emails is still an open implementation
  question (`data-model.md` §Indexes note — `PasswordReset.userId`-keyed counting only works for
  known accounts; unregistered emails need a separate IP-based or ephemeral counter). Consider an
  ADR if that mechanism turns out to need new infrastructure (e.g., a shared cache) rather than
  an in-memory counter.
- No other decision in these five flows rises to ADR-worthy — token consume-on-use atomicity is
  already covered by the existing ADR-0001, and session invalidation by ADR-0002.
