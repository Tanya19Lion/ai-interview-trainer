# PRD — AI Interview Trainer

> **Inputs:** no `idea-brief.md`/`CONTEXT.md` pair exists at project scope — those live only
> per-feature under `docs/features/*/`. This PRD is a retrofit against the already-built app;
> its factual inputs are the codebase itself (`src/`, `client/`) and [CONTEXT](./CONTEXT.md).
> **Reference module:** the whole codebase — `src/` (Express + TypeScript + Mongoose) and
> `client/` (Vite + React 19 + TypeScript), independently typed, no shared package.
> **External context channels used:** None.

## 1. Context

A job-seeker preparing for a technical interview (React, JavaScript, Node.js, TypeScript,
Next.js, CSS, HTML, SQL, REST API) wants to practice: pick a topic and a level
(Junior/Middle/Senior), get AI-generated questions, type a text answer, and immediately see
structured feedback — a score, an explanation of mistakes, a correct answer, and a list of weak
topics to review. Without a tool like this, a job-seeker either studies from static question
lists with no personalized feedback, or pays for a live mock-interviewer.

The project started as static HTML mockups (`diff-*.html`) that fixed the visual language (a
"git diff / code review" feedback style). This PRD is written now that `client/` already matches
all three mockups functionally and visually (all 10 tasks from the original client plan are
shipped per `PROGRESS.md`), and the backend (`src/`) is a working full-stack service with real
authentication, AI integration, and MongoDB persistence. The document records what has been
built and why, as a contract for future changes — not a pre-build spec.

The accepted vector (already implemented, not hypothetical): an Express + TypeScript + Mongoose
backend, a separate Vite + React 19 SPA client, with answer evaluation fully delegated to an
external AI provider (Anthropic API) — no in-house ML model.

## 2. Goals

- Job-seeker picks a topic and a level, gets an AI-generated question, submits an answer, and
  sees structured feedback (score 0–10, explanation, correct answer, weak topics) with no
  manual page reload.
- Job-seeker authenticates via Google OAuth or email/password and gets a persistent JWT session
  (httpOnly cookie).
- A completed interview session is stored, and the job-seeker sees history and stats (pass rate
  by topic and level) without redoing the session.
- Client and server stay independently typed projects with no shared npm package — a deliberate
  trade-off for a single maintainer, not an oversight.

## 3. Non-goals

- Voice/video interviews or a live sandboxed code editor — only text answers, evaluated by AI as
  a diff/code-review.
- Multi-user teams, roles (admin/reviewer), paid tiers — a single role, job-seeker, running a
  self-directed session.
- An in-house ML model for answer evaluation — fully delegated to an external AI API
  (`ANTHROPIC_API_KEY`), nothing trained locally; provider swap is isolated in
  `src/services/ai.service.ts`.
- A formal migration tool for the MongoDB schema — `make migrate` stays a documentation
  placeholder until the document shape stabilizes (ADR-0001).

## 4. User stories

### US-01: Pick a topic and a level

**As a** job-seeker
**I want** to pick a subject area (React/JavaScript/Node.js/TypeScript/...) and a level
(Junior/Middle/Senior)
**So that** the questions I get match where I actually am in my preparation

### US-02: Get an AI-generated question

**As a** job-seeker
**I want** to see a question generated by AI for my chosen topic and level
**So that** I practice on fresh questions instead of a memorized set

### US-03: Submit an answer and get feedback

**As a** job-seeker
**I want** to type a text answer and immediately get a score, an explanation, and a correct
answer
**So that** I understand my mistakes right away, not after the whole session ends

### US-04: Authenticate

**As a** job-seeker
**I want** to log in via Google OAuth or email/password
**So that** my progress and history are tied to me and don't disappear between visits

### US-05: Review interview history

**As a** job-seeker
**I want** to see my past sessions with their questions/answers/scores
**So that** I can go back to a specific session and revisit my weak spots

### US-06: See stats

**As a** job-seeker
**I want** to see aggregated pass-rate stats by topic and level
**So that** I know which topic to brush up on before my next attempt

## 5. Acceptance criteria

### AC-01 (US-01, US-02, US-03) — happy path

**Given** an authenticated job-seeker with no active session
**When** the job-seeker picks a topic and a level, starts a session, and submits an answer to
each question received
**Then** the system shows the job-seeker a score, explanation, correct answer, and weak topics
for each answer, and stores the completed session in history

### AC-02 (US-04) — error

**Given** a job-seeker submits an email/password login
**When** the password does not match the stored hash
**Then** the system blocks the login and tells the job-seeker the email/password combination is
invalid, without revealing whether that email exists

### AC-03 (US-04, US-05, US-06) — authorization

**Given** a request carries no valid JWT (missing or expired)
**When** the job-seeker attempts to open a protected area (start a session, history, stats)
**Then** the system denies access without performing the requested action

### AC-04 (US-01, US-03) — domain invariant

**Given** a job-seeker's interview session is already marked completed
**When** the job-seeker attempts to submit another answer into that same session
**Then** the system blocks the action and tells the job-seeker the session is already complete —
a new one must be started

### AC-05 (US-05, US-06) — cross-context

**Given** interview sessions belonging to other job-seekers exist in the system
**When** a job-seeker opens their own history or stats
**Then** the system shows only sessions owned by that job-seeker (ownership filtering happens at
the data-access layer, not at the UI layer)

## 6.1 Security / privacy

- **Data classification:** Internal — contains job-seeker personal data, not public, not a
  regulated category (no payment/health data).
- **Personal data touched:** `email`, `name`, `avatarUrl`, `googleId` (`User`); `passwordHash`
  (bcryptjs hash, never the raw password); the job-seeker's answer text and the AI feedback tied
  to it (`InterviewSession.questions`).
- **AuthZ/AuthN impact:** every route under `/api/interview`, `/api/history`, `/api/stats` is
  guarded by `middleware/auth.ts` (`requireAuth` — JWT check via httpOnly cookie); controllers
  filter by the `userId` taken from the token, never from the request body.
- **Abuse cases:**
  - **Cross-job-seeker access:** mitigated by filtering every query by `userId`
    (`InterviewSessionModel.find({ userId })`) at the data-access layer, not at the UI.
  - **Password brute-force on `/api/auth/login`:** no rate limit exists yet — open question, §8.
  - **Google OAuth token forgery:** mitigated by verifying the token server-side via
    `google-auth-library` against `GOOGLE_CLIENT_ID` (the server never trusts a client-supplied
    payload without verification).
- **Security review:** N/A for the current state (single maintainer, no regulated PII category)
  — but a rate limit on the auth routes should land before any public/production release (§8).
